# Historical efficiency

An expandable KPI strip above Latest Call compares the selected thread's lifetime usage with all imported local primary chats, including saved summaries whose source files are no longer present. Comp defaults to seven UTC calendar days, including today; 30 days and all history are available. Archived chats participate regardless of picker filters. Import runs in the background, and the banner reports progress and failed reads.

The compact strip has shared Thread and Comp rows. Displayed deltas compare their visible aggregate values directly; these aggregate comparisons are the sole spending comparison, with explicit coverage and provisional states; see [Dashboard redesign](DASHBOARD-REDESIGN.md) for thresholds, settings, insights and validation.

Cost per call divides priced normal-call cost plus separately estimated compaction charges by priced normal calls. Context cost per call independently prices fresh, cached and cache-write input, even when output is unavailable. Reasoning is already included in output and is never charged twice. Missing categories and unsupported rates are excluded, with qualifying counts and pricing coverage shown. Partial spending is a lower bound, not a complete bill.

The Comp row includes all imported calls in the selected UTC period, including the selected chat; its preceding-period comparison uses the immediately preceding equal-length period. All history has no preceding-period comparison. Analytics activation is recorded independently. New rates trigger source replay for historical aggregates and payback when the source remains readable. Saved estimates whose source is missing retain their original calculation basis and remain visible, with affected comparisons marked provisional. Pricing identity includes both metadata and the bundled rate table.

Periods use UTC calendar days. Averages are weighted sums divided by qualifying counts. Latest-100 windows use retained normal calls, including unpriced calls in the window; separately attributed compaction charges within that window are included. Routine snapshots carry aggregate summaries and selected recent calls, without loading or transmitting lifetime call lists or weekly tables. Missing or zero references have no percentage change.

## Compaction estimates

The compacted path uses recorded subsequent call categories and output. The alternative retains the removed context as an additional warm prefix, priced under each subsequent call's model, tier, region and input-size band. Reported retained context is used when available; otherwise 40,000 tokens is assumed. When a compaction record has matching nonempty compaction and usage response IDs and valid token categories, its recorded request usage replaces the modeled request charge. Input, cache reads, cache writes and output use the existing model/tier/region and full-request pricing rules; reasoning is included in output once. Surrounding model metadata is used, with Standard assumed when the tier is missing. Missing, mismatched or invalid usage falls back to a warm read of the original context and 3,600 summary output tokens, labeled Estimated. Valid recorded tokens with unavailable pricing remain visible with unavailable cost.

The full attributed charge adds a modeled replacement-context write to the request cost, then credits replacement writes recorded on the first subsequent normal call once. A recorded request plus an outstanding modeled write is labeled Partly estimated; its recorded token counts remain identified separately. The graph, thread spending, cost/call and historical payback use this same charge. Compactions do not increase normal-call or turn counts, or change the prospective Compaction Value forecast. Latest-100 spending includes trailing compaction charges after the last normal call.

An epoch is profitable when cumulative estimated savings first reach its overhead. The details expose first break-even call and final net savings, which can differ from the earlier break-even result. Invalid counterfactuals, unavailable pricing/accounting, and context-capacity violations exclude an epoch from the denominator. A complete compaction with no subsequent calls is unprofitable when its overhead can be priced.

The next compaction, an explicit SessionEnd, or seven days without recorded activity closes an epoch. A response ending does not close it. Inactivity closure is labeled and counted; resumed activity replays and recalculates the final epoch. Period payback counts completion dates, while spending counts charge dates. No evaluable outcomes means N/A.

## Storage and recovery

The private `efficiency.sqlite` in each plugin state directory is durable storage for imported numeric telemetry. DEV and release keep separate databases. Typed tables hold recent calls and numeric lifecycle boundaries, daily aggregates, materialized totals by pricing dimension, compaction outcomes, and small import checkpoints. Model/pricing dimensions and calculation definitions are interned. Chat labels and workspace names support saved-chat selection; prompts, excerpts, tool arguments, transcript content and reasoning text are not retained. Codex databases and transcripts remain read-only.

Recent call, turn, compaction-boundary, numeric compaction-usage, charge and replay detail expires after 90 UTC calendar days including today. Daily spending and completed-compaction summaries remain permanently. Small current-epoch/parser checkpoints retain the state required to continue an active chat. Retention therefore limits detailed history rather than imposing a fixed database size. Missing source files do not erase imported summaries; saved chats remain searchable, with source availability and retained-detail coverage disclosed.

Existing lifecycle hooks import only their affected chat, even without an open panel. Each invocation reads at most 4 MiB of transcript body and targets 500 ms of ingestion, checking its time budget between complete records. Header/checkpoint verification and transaction commit add bounded overhead; the time target is not a hard real-time guarantee. Incomplete records stay in the source file. Work that exceeds a batch resumes at the next hook or panel import; disabled hooks or source loss before import cannot be recovered by the database.

A lazy worker shared by a server's panels performs backfill, compatible repricing and retention. It is not a detached service. Imports commit numeric contributions and their byte checkpoint together. Replacement, truncation and checkpoint changes trigger a staged rebuild; the previous contribution remains published until replacement completes. Replay fingerprints and numeric checkpoints prevent duplicate accounting across process restarts. No raw partial lines are saved in checkpoints. Old replay windows are bounded during backfill and expired keys are removed incrementally.

Normal refreshes reuse catalogue metadata and stat signatures, importing only selected/hook activity. Full discovery is reserved for opening, discovery changes and explicit rescan. Historical queries use indexed daily data and materialized lifetime totals. Snapshots are cached by storage revision, chat, UTC day and import state, limited to 64 entries and 16 MiB of serialized results; that limit is not a total-process RAM cap. Unchanged historical refreshes do not rewrite analytics or read transcript bodies. Live transcript tails also skip reads when their identity and stat signature are unchanged.

Schema v4 adds bounded numeric compaction details, provenance and charge components without storing summaries, replacement history or transcript text. Accounting basis v5 rebuilds readable sources through staged import; unavailable sources retain their prior calculation basis. Complete retained numeric sequences preserve recorded compaction usage during compatible repricing.

Legacy per-chat JSON migrates one chat per transaction and is removed only after conversion. Unused deprecated comparison metadata is ignored and left untouched. Compatible retained numeric sequences can be replayed for repricing, including compactions when their required context is complete. Partial retained days can reprice ordinary calls when completeness is established. Older or incompatible estimates remain visible under their recorded calculation version; mixed historical versions make comparisons provisional.

The bundled runtime includes a SQLite version with the multi-connection WAL-reset fix; unsupported older runtimes pause durable history rather than risking the database. SQLite uses WAL, durable commits, short transactions, bounded lock waits and an approximately 4 MiB automatic checkpoint target. The journal target is not an absolute cap while readers or writes are active. Maintenance prunes bounded batches, checkpoints the journal and incrementally vacuums fresh stores. Migrated databases reuse free pages without an automatic full-database vacuum. No recurring backups or snapshot archives are created. Storage errors preserve the last committed cursor/data and surface paused collection while live telemetry continues. A database from a newer schema is not reset or overwritten.

Use **Settings → History storage → Inspect storage** to read database/journal bytes, reusable space, retention, import backlog and frozen-version coverage on demand. These diagnostics do not run on every poll.

## Validation

Run `npm --prefix plugins/token-monitor-embedded run history:bench` for the reproducible scale fixture: one million calls across 10,000 chats, 100,000 recent detailed calls, realistic numeric checkpoints, append-only import and ten source replacement/retention cycles. The fixture is temporary and removed afterward. [Recorded measurements](HISTORY-BENCHMARK.json) include Node/SQLite versions, storage and journal bytes, RSS growth, and timings. Cached cold means a reopened store with the OS file cache warm; timings exclude MCP transport and UI rendering. RSS growth describes the benchmark process, not a guaranteed application memory limit.

On the bundled macOS ARM64 Node 24.21.0 / SQLite 3.53.4 runtime, the recorded run passed the p95 targets of 50 ms warm and 250 ms cached cold. The database was approximately 107 MiB with detail and 37 MiB after expiry, with no backup copies. Repeated replacement/prune cycles stabilized around 35 MiB. These are synthetic workload measurements, not a hard storage cap or a promise for every machine.

The automated suites cover accounting parity, partial lines, large records, duplicate/replayed events, transaction rollback, retention, orphaned legacy data, compatible repricing, compaction closure, hook-only collection, and fresh DEV MCP restart/source restoration. The bundled panel's on-demand storage settings were inspected at 600 px and 320 px widths. Installed desktop presentation still requires the host restart that loads a newly installed DEV build.
